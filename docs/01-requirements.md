# 01. 要件定義

## 1. 用語

| 用語 | 定義 |
|---|---|
| 組織 (organization) | 参加企業。招待コードの発行単位 |
| 参加者 (profile) | 招待コードで登録した個人。`auth.users` と 1:1 |
| 匿名ID | `KRY-4821` 形式の表示用ID。参加者を特定しない |
| 実名情報 (identity) | 氏名・会社名・部署・一言。相互accept まで非公開 |
| ペルソナ (persona) | インタビュー回答から生成した、アバターの振る舞い定義 |
| マッチ (match) | 参加者2名の組。会話ログと相性レポートを1つずつ持つ |
| 判断 (decision) | マッチに対する `accept` / `decline` |
| 相互accept | マッチの両参加者が `accept` した状態。ここで初めて実名が開示される |

## 2. 機能要件

### FR-1. 登録

| ID | 要件 |
|---|---|
| FR-1.1 | 参加者はメールアドレスでOTPログインできる |
| FR-1.2 | 初回ログイン後、勤務先から配布された招待コードの入力を求められる |
| FR-1.3 | 招待コードが無効・期限切れ・利用上限超過の場合はエラーを表示し、登録は完了しない |
| FR-1.4 | 有効なコードで登録すると、参加者は該当組織に所属し、匿名IDが自動採番される |
| FR-1.5 | 参加者は実名情報（氏名・会社名・部署・年代・一言）を登録する。これはアプリ内のどこにも表示されない |
| FR-1.6 | 登録済みの参加者が招待コード画面に来た場合はホームへリダイレクトする |

### FR-2. AIインタビュー

| ID | 要件 |
|---|---|
| FR-2.1 | 有効な設問を `order` 順に1問ずつチャット形式で提示する |
| FR-2.2 | 選択式は選択肢ボタン、自由記述はテキスト入力で回答する |
| FR-2.3 | 空文字・空白のみの回答は送信できない |
| FR-2.4 | 回答は1問ごとに永続化され、途中離脱しても続きから再開できる |
| FR-2.5 | 全問回答後「アバターにまかせる」でインタビューを完了し、ペルソナ生成をキックする |
| FR-2.6 | ペルソナ生成が失敗しても、参加者の画面は待機状態に進む（バッチで再試行） |
| FR-2.7 | 参加者はマイページで自分の回答を再閲覧できる |

### FR-3. マッチング（バッチ）

| ID | 要件 |
|---|---|
| FR-3.1 | ペルソナ生成済みの参加者どうしを、同一組織以外の組み合わせで候補化する |
| FR-3.2 | 同じ2名の組み合わせは1度しか候補化しない |
| FR-3.3 | 候補ごとにアバター間会話を生成する（既定8〜12ターン） |
| FR-3.4 | 会話ログから5軸の相性レポートを生成する |
| FR-3.5 | 総合スコアが通知閾値（既定75）以上のマッチのみ、両参加者に通知を作成する |
| FR-3.6 | 閾値未満のマッチは通知せず、参加者からも参照できない |
| FR-3.7 | バッチは1回の実行で処理する候補数に上限を設け、途中失敗しても次回に再開できる |
| FR-3.8 | バッチのエンドポイントは cron シークレットで保護する |

### FR-4. 通知

| ID | 要件 |
|---|---|
| FR-4.1 | 通知一覧で未読/既読を区別して表示する |
| FR-4.2 | ヘッダーのベルに未読件数バッジを表示する |
| FR-4.3 | 通知をタップすると既読化し、対象の相性レポートへ遷移する |
| FR-4.4 | 通知が0件のときは空状態を表示する（エラーにしない） |

### FR-5. 会話ログ・相性レポート

| ID | 要件 |
|---|---|
| FR-5.1 | 相手は匿名ラベル（例:「お相手 A さん」）で表示し、実名・所属は表示しない |
| FR-5.2 | アバター間会話の全ターンを、話者（あなたのアバター / お相手のアバター）付きで表示する |
| FR-5.3 | 5軸それぞれのスコア・バー・所見・引用を表示する。`conflict` 軸には「低いほど良い」を明示する |
| FR-5.4 | 総評を表示する |
| FR-5.5 | 未判断のときのみ「会う」「今回は辞退する」を表示する |
| FR-5.6 | 「今回は辞退する」は確認シートを挟む |
| FR-5.7 | 判断は1マッチにつき1回のみ記録し、以降は変更できない |
| FR-5.8 | 自分の判断は相手から参照できない |

### FR-6. 実名開示

| ID | 要件 |
|---|---|
| FR-6.1 | 相互acceptが成立したマッチでのみ、相手の実名情報を取得できる |
| FR-6.2 | 自分だけがacceptした状態では、相手の実名情報を一切取得できない（相手の判断の有無も分からない） |
| FR-6.3 | 相互accept時、マッチに面談候補日時が3件用意される |
| FR-6.4 | 参加者は候補日時を1つ選んで送信できる。未選択では送信ボタンを無効にする |
| FR-6.5 | 両者が同じ枠を選んだ場合に日程確定とする（片方のみの場合は「相手の回答待ち」） |

### FR-7. 辞退

| ID | 要件 |
|---|---|
| FR-7.1 | 辞退したマッチは以降、通知にも一覧にも現れない |
| FR-7.2 | 辞退した事実は相手に通知されない |
| FR-7.3 | 辞退後もアバターは他の候補との会話を継続する |

### FR-8. 補助画面

| ID | 要件 |
|---|---|
| FR-8.1 | ホームに現在の状況・5段階ステップ・最新のお知らせ・メニューを表示する |
| FR-8.2 | プライバシー説明・FAQ を静的ページとして提供する |
| FR-8.3 | 設定で通知のオン/オフを切り替えられる |
| FR-8.4 | 設定からアカウントと全データを削除できる |

## 3. 非機能要件

| ID | 要件 |
|---|---|
| NFR-1 | **匿名性**: 実名情報の漏洩経路をアプリ層に依存させず、Postgres の RLS で遮断する。サービスロールキーはブラウザに露出させない |
| NFR-2 | **判断の非対称性**: 相手の判断状態は、相互acceptが成立するまで一切取得できない。「未判断」と「辞退」がクライアントから区別できないこと |
| NFR-3 | **人事非閲覧**: 組織管理者向けのマッチ閲覧手段を実装しない。集計は組織単位の匿名カウントのみ |
| NFR-4 | **可用性**: Claude API が利用不可でも、決定的フォールバックにより全画面が動作する |
| NFR-5 | **アクセシビリティ**: PoC 相当を維持（`aria-live`、フォーカス移動、`prefers-reduced-motion` 対応、スクリーンリーダー用テキスト） |
| NFR-6 | **モバイル前提**: 375×812 を基準とし、`window.confirm` は使わずボトムシートで確認する |
| NFR-7 | **国際化**: 表示文言は日本語。文言はコンポーネントに直書きせず定数にまとめる |
| NFR-8 | **型安全**: TypeScript strict。DB型は Supabase から生成した型を使う |
| NFR-9 | **秘匿情報**: `ANTHROPIC_API_KEY` / `SUPABASE_SERVICE_ROLE_KEY` / `CRON_SECRET` はサーバー専用。`NEXT_PUBLIC_` を付けない |

## 4. 受け入れ基準（抜粋）

- [ ] `npm run build` と `npm run typecheck` と `npm run lint` が通る
- [ ] `npm test` が通る
- [ ] 招待コードなしで `/interview` 等へ直接アクセスすると `/invite` へリダイレクトされる
- [ ] 片側だけ accept した状態で相手の `identities` 行を SELECT しても 0 行が返る（RLSテスト）
- [ ] 相手の `match_decisions` 行を SELECT しても 0 行が返る（RLSテスト）
- [ ] `ANTHROPIC_API_KEY` を外した状態でバッチを流しても、会話ログと相性レポートが生成される
- [ ] 通知閾値未満のマッチが参加者から参照できない
