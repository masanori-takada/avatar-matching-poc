# 00. 資料概要 — AIアバター自動マッチング

## 1. プロダクトの一行説明

> **AIが代わりに会っている。**

利用者は最初に6問のインタビューに答えるだけ。以降は本人のAIアバターが、他の参加者のアバターと自動で会話し続ける。相性が基準を超えたときにだけ通知が届き、利用者は「アバター同士の会話ログ」と「相性レポート」を読んでから、会うかどうかを判断する。

## 2. 前提となる体験設計（PoCから確定済み）

PoC (`poc/index.html`, `poc/app.js`, `poc/style.css`) は、企業間マッチング（例: 刈谷市の参加企業）を想定した iPhone サイズのモックである。本番実装はこの体験を仕様の正典として扱う。

### 2.1 中核となる価値

| 原則 | 具体的な現れ方 |
|---|---|
| **本人は動かない** | 会話・スクリーニングはアバターが全部やる。本人が対応するのは最後の「会う / 辞退」判断だけ |
| **断られる体験が発生しない** | 辞退は相手に一切通知されない。相手からは「まだ返事がない」と「辞退された」が区別できない |
| **匿名性が前提条件** | 実名・所属はアプリのどこにも出ない。**両者が「会う」を選んだ後にのみ**、お互いにだけ開示される |
| **人事も運営も見られない** | 誰と会話しているか、どんなマッチが成立したかを、勤務先の人事・サービス運営者が閲覧できない |
| **通知が来ないことは失敗ではない** | 相性基準を満たさなければ何も起きない。「マッチしませんでした」という通知も出さない |

この5つは UI の飾りではなく、**データベースの権限設計 (RLS) で担保すべき要件**である。詳細は `03-data-model.md` を参照。

### 2.2 画面フロー

```
[1] 招待コード入力
      │ 勤務先から配布されたコードで登録
      ▼
[2] AIインタビュー（6問: 選択式4 + 自由記述2）
      │ 「アバターにまかせる」
      ▼
[3] アバターが会話中（待機）
      │ ステップインジケーター 5段階
      │ 相性基準を満たしたときだけ通知
      ▼
[4] お知らせ一覧 ──┐
      │            │
      ▼            ▼
[5] 会話ログ・相性レポート
      │   ├─「今回は辞退する」→ [5b] 辞退完了（相手に通知されない）
      │   └─「会う」
      ▼
[6] 実名開示（相互accept時のみ）
      │ 面談候補日時を選択
      ▼
[7] 日程送信完了
```

補助画面: ホーム / マイページ / プロフィール / プライバシー / よくある質問 / 設定

### 2.3 相性レポートの5軸

PoC で定義済みの評価軸をそのまま採用する。

| キー | ラベル | 方向 |
|---|---|---|
| `flow` | 会話の弾み | 高いほど良い |
| `values` | 価値観の一致 | 高いほど良い |
| `humor` | ユーモアの相性 | 高いほど良い |
| `interest` | 相互関心 | 高いほど良い |
| `conflict` | 不一致の重大度 | **低いほど良い** |

各軸は `score`(0–100) / `comment`(所見) / `quote`(会話ログからの根拠引用) を持つ。引用は必ず実際の会話ログ中の発言から取る（後述の検証を通す）。

### 2.4 インタビュー設問（初期セット）

| # | 種別 | 設問 |
|---|---|---|
| q1 | 選択 | 休日の過ごし方に近いのはどちらですか? |
| q2 | 選択 | 初対面の人と話すとき、あなたは? |
| q3 | 自由 | 最近、思わず時間を忘れて夢中になったことは何ですか? |
| q4 | 選択 | 一緒にいて心地よいと感じるのは、どんな人ですか? |
| q5 | 選択 | 将来について、今の気持ちに近いのは? |
| q6 | 自由 | 相手に、これだけは知っておいてほしいことはありますか? |

設問は DB 管理とし、コード変更なしに差し替え・追加できるようにする。

## 3. PoC と本番実装の差分

| 項目 | PoC | 本番実装 |
|---|---|---|
| 認証 | なし（招待コードは空欄チェックのみ） | Supabase Auth（メールOTP）+ 招待コード検証 |
| データ | `localStorage` | Supabase Postgres + RLS |
| 相手 | 固定NPC 1名 | 実参加者どうしのマッチング |
| 会話 | ハードコードされた9ターン | Claude API によるアバター間会話生成 |
| 相性判定 | 固定スコア | Claude API による5軸評価 + 決定的フォールバック |
| 通知 | `setTimeout` 6秒 | DB通知テーブル + ポーリング（将来Web Push） |
| 実名開示 | 常に固定値を表示 | RLS で相互accept時のみ取得可能 |
| 画面 | 素のDOM操作 1ファイル | Next.js App Router + React Server Components |

## 4. 本番実装のスコープ

### 対象（このリポジトリで実装する）

- Next.js 15 (App Router) によるフロントエンド全画面
- Supabase スキーマ・RLSポリシー・マイグレーション
- 招待コードによる組織所属登録
- インタビュー → ペルソナ生成
- マッチング候補選定 → アバター間会話生成 → 相性評価（バッチ）
- 通知・判断・相互開示・日程調整
- Claude API 連携（フォールバック付き）
- 単体テスト（スコアリング・RLS前提のロジック）

### 対象外（今回は実装しない）

- Web Push / メール送信の実配信（インターフェースのみ定義）
- 管理画面（組織・招待コードの発行は SQL / Supabase Studio で運用）
- 決済・課金
- ネイティブアプリ
